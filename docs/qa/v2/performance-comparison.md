# Performance comparison: V1 vs V2 before optimisation vs V2 after optimisation

Tool: `tests/agent-qa/perf/measure-app.mjs` (tables generated by `tests/agent-qa/perf/compare.mjs`).
Sources: `baseline-perf-v1.json`, `perf-v2-before-opt.json`, `perf-v2-after-opt.json`, `perf-v2-ab-coldload.json`.
Chromium 141 emulation (iPhone SE 3rd gen, iPhone 14, iPhone 15 Pro Max viewports), RUNS=3 medians, fresh browser context per run.

## What changed (V2 after)

| Change | Files | Effect measured |
| --- | --- | --- |
| `search-index.json` (257 KB) no longer fetched at startup. New `loadSearchIndex()` fetches it on first visit to `#/search`; `search.js` shows "loading" text meanwhile and an error notice if the fetch fails. | `js/data.js`, `js/search.js`, `js/app.js` | -257 KB and -1 request on every cold load |
| `variants.json` (3 bytes, `[]`, read by no module) removed from the startup fetch list. | `js/data.js` | -1 request |
| `question-audit.json` (24 KB, only used by the startup integrity check) fetched after the first render via `loadQuestionAudit()`; a mismatch still replaces the screen with the same integrity error as before, a fetch failure only logs a warning. | `js/data.js`, `js/app.js` | -24 KB and one fewer request before first paint (still fetched right after) |
| Hero image hints `decoding="async"` and `fetchpriority="high"` (image file not touched). | `js/home.js` | within noise; kept because LCP did not get worse |
| Cache name and `?v=` bumped to `v2c` so the new JS is not served from the old cache-first service-worker cache. All data files stay in `APP_SHELL`, so search works offline (checked). | `sw.js`, `index.html` | none (correctness) |
| Self-check summary scroll fix (visual bug, not performance). | `js/practice-selfcheck.js`, `css/styles.css` | n/a |

Tried and rejected (measured, interleaved A/B on iPhone 14 at 4x CPU, median of 9 cold loads): `<link rel="modulepreload">` for all 37 modules raised FCP from about 210 ms to about 276 ms; a `preload as=fetch` of the 7 startup JSON files alone did not help (FCP 208, LCP 548 ms vs 196/508 ms with neither). Neither is in the final code.

## Honest notes

- Chromium emulation on a local server, not iOS Safari. The local server does not compress responses, so "transferred" equals raw size (CSS 335 KB here is about 52 KB gzip on Vercel). Network time is near zero, so latency effects (a 3-deep module waterfall: app.js -> ui/data/home -> practice-*) are not visible here and not addressed.
- The "V2 before" and "V2 after" full runs were taken about 30 minutes apart; the controlled A/B above is the better evidence for cold load. Route and interaction numbers move by 10 to 40 ms between identical runs at 4x CPU (see rounds in `perf-v2-ab-coldload.json`); the optimisation does not touch those paths, so differences there are noise, not gains.
- `n/m` routes (`#/questions?view=deck`, `#/settings`): these render synchronously, so the script's `aria-busy` observer never fires and it records its 10 s timeout. This also happens in V1; the value is a measurement artifact, not a slow route. Deck interactions are covered by the in-page table.
- V2 remains slower than V1 at startup on this setup (for example iPhone 14 4x: FCP 136 -> about 192 ms, DCL 245 -> about 317 ms; V1 JS 326 KB vs V2 432 KB, CSS 207 KB vs 336 KB, 43 vs 49 requests). The optimisation recovered the extra JSON weight but not the larger CSS/JS. The next candidates, not done because they are bigger changes than "minimal and safe": trim the layered CSS overrides in `styles.css` (about 130 KB over V1), and lazy-load rarely used modules (`print-book.js`, `report.js`, `practice-a1..a5.js`, `recorder.js`) with dynamic `import()`.
- The remaining first-render long tasks at 4x CPU (two per load, 54 to 92 ms TBT) are the initial style/layout of the 335 KB stylesheet and the first home render continuing after IndexedDB opens; both were present before this change.
- `question-audit.json` is still fetched right after first render, so it appears in the request count (49 = 51 - search-index - variants).
